# 从「状态锁」到「节流 + 状态锁」：一次按钮防重复提交的交互优化复盘

关键词：防抖（debounce）、节流（throttle）、闭包陷阱、useRef、loading 闪烁、自定义 Hook、ahooks

## 一、背景

同一个「提交 / 搜索」类交互，代码从“能跑”到“能扛”，往往要经过三代演进：

| 代际 | 方案 | 一句话定位 |
| --- | --- | --- |
| V0 | 纯 useState 状态锁 | 入门级合格实现 |
| V1 | 裸节流函数包裹 | 思路对，但保护不完整 |
| V2 | 节流 + ref 状态锁 + loading | 生产级优雅实现 |

下面逐代拆解问题，并给出可以直接落地的封装方案，同时补充基于 ahooks 生态的替代实现，避免从零手写重复逻辑。

## 二、V0：未优化版本（纯状态锁）

### 2.1 常见写法

```jsx
import { useState } from 'react';

function SubmitForm() {
  const [loading, setLoading] = useState(false);

  const handleSubmit = async () => {
    if (loading) return; // 想用它拦截重复点击
    setLoading(true);

    await fetch('/api/submit', { method: 'POST' });

    setLoading(false); // 请求结束才解锁
  };

  return (
    <button onClick={handleSubmit} disabled={loading}>
      {loading ? '提交中...' : '提交'}
    </button>
  );
}
```

### 2.2 五个隐藏问题

**问题 1：状态锁存在闭包陷阱，拦不住极速连点**

handleSubmit 每次渲染都会重新创建，闭包捕获的是那一次渲染时的 loading。React 的 state 更新是异步批处理的：

- 第 1 次点击：闭包里 loading === false，通过判断 → setLoading(true)（尚未生效）
- 第 2 次点击（如果发生在重新渲染之前）：闭包里 loading 仍然是 false → 又通过判断，再次提交

`if (loading) return` 读的是渲染快照，不是实时值。在重新渲染前到达的连点会被漏掉，所以它只是“看起来”能拦截。

**问题 2：没有 try/finally，异常即锁死**

fetch 一旦抛错（网络抖动、接口 500、用户取消），setLoading(false) 永远不会执行，按钮永久禁用，用户只能刷新页面。

**问题 3：接口太快时 loading 闪烁**

提交接口 30ms 就返回，按钮会瞬间在“提交 → 提交中... → 提交”之间闪一下，视觉上像界面卡顿。

**问题 4：缺少冷却窗口**

状态锁只保证“请求进行中不重复提交”，但请求一旦返回，用户立刻猛点，依然会连发多次请求。对于幂等性差的接口，这是真实风险。

**问题 5：逻辑零复用**

每加一个提交按钮，就要把 loading state、判断、重置逻辑再抄一遍，散落在各个组件里。

## 三、V1：裸节流版本

```jsx
const throttledSubmit = throttle(handleSubmit, 1000);

return <button onClick={throttledSubmit}>提交</button>;
```

节流解决了 V0 的「冷却窗口」问题，但引入了新问题：

1. **保护不完整**：节流只拦 1000ms 时间窗口。如果请求耗时 1500ms，冷却窗口一过，用户仍能再次点击，重复提交照样发生。
2. **零用户反馈**：点击后被静默拦截，用户看不到任何“处理中”提示，会误以为按钮失灵，于是更用力地连点。
3. **定时器/时间戳残留**：自写的朴素节流常忽略暴露 cancel（lodash 等成熟实现是有的），组件卸载后定时器可能仍在等待回调。

结论：节流负责“频率控制”，不应独自承担“防重复提交”，它必须和状态锁配合。

## 四、V2：节流 + 状态锁 + loading 的优雅实现

V2 的防护分三层：

- **ref 状态锁**：请求进行中，run 内部同步拦截，不依赖渲染。
- **节流冷却**：请求结束后的一段时间内，压制高频重复触发。
- **最小 loading 时长**：无论成功失败，loading 至少展示 minLoadingTime，消除闪烁。

```jsx
import { useState, useCallback, useRef, useEffect } from 'react';

const sleep = (ms: number) => new Promise<void>((resolve) => setTimeout(resolve, ms));

/**
 * 保证任务至少耗时 minMs：成功、失败路径都兜底
 */
async function runWithMinLoading<T>(task: () => Promise<T>, minMs: number): Promise<T> {
  const start = Date.now();
  try {
    return await task();
  } finally {
    const elapsed = Date.now() - start;
    if (elapsed < minMs) await sleep(minMs - elapsed);
  }
}

type RejectReason = 'running' | 'throttled';

interface ThrottleActionOptions {
  /** 节流冷却时间，默认 1000ms，从本次触发时刻开始计算 */
  delay?: number;
  /** 最小 loading 展示时长，默认 300ms */
  minLoadingTime?: number;
  /** 被拦截时的回调，可用于 toast 提示 */
  onReject?: (reason: RejectReason) => void;
}

/**
 * 带状态锁、节流冷却、最小 loading 时长的异步动作 Hook
 */
function useThrottleAction<T extends (...args: any[]) => Promise<any>>(
  asyncAction: T,
  options: ThrottleActionOptions = {}
) {
  const { delay = 1000, minLoadingTime = 300, onReject } = options;

  const [isLoading, setIsLoading] = useState(false);
  const runningRef = useRef(false); // 状态锁：请求进行中
  const lastExecuteTimeRef = useRef(0); // 节流：上一次触发时间
  const isMountedRef = useRef(true);
  const onRejectRef = useRef(onReject);

  useEffect(() => {
    onRejectRef.current = onReject;
  });

  useEffect(() => {
    isMountedRef.current = true;
    return () => {
      isMountedRef.current = false;
    };
  }, []);

  const run = useCallback(
    async (...args: Parameters<T>) => {
      // 第一道防线：状态锁，请求进行中直接丢弃
      if (runningRef.current) {
        onRejectRef.current?.('running');
        return;
      }

      // 第二道防线：节流冷却，窗口内的触发直接丢弃
      const now = Date.now();
      if (now - lastExecuteTimeRef.current < delay) {
        onRejectRef.current?.('throttled');
        return;
      }

      runningRef.current = true;
      lastExecuteTimeRef.current = now;
      if (isMountedRef.current) setIsLoading(true);

      try {
        // 真实请求 + 最小展示时长，成功失败都兜底
        await runWithMinLoading(() => asyncAction(...args), minLoadingTime);
      } finally {
        // 第三道防线：无论成功失败都解锁，杜绝按钮永久禁用
        runningRef.current = false;
        if (isMountedRef.current) setIsLoading(false);
      }
    },
    [asyncAction, delay, minLoadingTime]
  );

  const reset = useCallback(() => {
    runningRef.current = false;
    lastExecuteTimeRef.current = 0;
    setIsLoading(false);
  }, []);

  return { run, isLoading, reset };
}

// 业务中直接使用
function SubmitForm() {
  const { run: handleSubmit, isLoading } = useThrottleAction(
    async () => {
      await fetch('/api/submit', { method: 'POST' });
    },
    {
      delay: 1000,
      minLoadingTime: 300,
      onReject: (reason) => {
        if (reason === 'throttled') {
          // 冷却期内点击，给用户一个轻提示，而不是静默丢弃
          console.info('操作太频繁，请稍后再试');
        }
      },
    }
  );

  return (
    <button onClick={handleSubmit} disabled={isLoading}>
      {isLoading ? '提交中...' : '提交'}
    </button>
  );
}
```

关于冷却语义：V2 的节流窗口从“本次触发时刻”开始计算，不是从“请求结束时刻”开始计算。如果请求耗时超过 delay，请求结束后可以立即再次触发。这是标准节流语义，适合大多数提交场景；若业务要求“请求结束后再冷却”，需在 finally 中把 lastExecuteTimeRef.current 更新为 Date.now()。

关于 reset：请求仍在飞行时调用 reset 会强制解锁，可能造成重入。仅在确定请求已废弃（如切换页面、取消提交）时使用。

## 五、三代方案横向对比

| 对比维度 | V0 纯状态锁 | V1 裸节流 | V2 节流 + ref 状态锁 |
| --- | --- | --- | --- |
| 极速连点拦截 | ⚠️ 重新渲染前可能漏 | ✅ 窗口内拦截 | ✅ ref 状态锁同步判断 |
| 请求耗时长时的重复提交 | ✅ 拦得住 | ❌ 冷却期一过就放行 | ✅ runningRef 拦住 |
| 异常兜底 | ❌ 可能永久禁用 | ❌ 无 | ✅ finally 必解锁 |
| loading 闪烁 | ❌ 常见 | ❌ 无反馈 | ✅ 最小展示时长，成功失败均兜底 |
| 冷却期点击反馈 | 无此概念 | ❌ 静默丢弃 | ✅ 可通过 onReject 提示用户 |
| 操作反馈 | 一般 | 无 | ✅ 明确加载态 |
| 代码复用性 | ❌ 每处复制 | 一般 | ✅ Hook 全局复用 |
| 内存/定时器管理 | 无 | ⚠️ 自写实现常忽略清理 | ✅ 卸载自动清理 |

## 六、核心技术点拆解

### 6.1 用 useRef 替代 useState 做锁

useRef 的 .current 是同步读写的，修改后立刻生效，不受渲染周期影响；而 useState 的值是渲染快照，在同一个事件循环里读不到最新值。凡是“标记位 / 计时器 / 上一次执行时间”这类数据，都应放在 ref 里。

### 6.2 try/finally 保证解锁

锁的产生和释放必须成对出现在 try/finally 中，异常路径同样要走到解锁逻辑，否则一次接口报错就会让按钮永久失效。

### 6.3 最小 loading 时长：成功和失败都要兜底

只写 `await Promise.all([realRequest, sleep(300)])` 是不够的：Promise.all 在 realRequest reject 时会立即 reject，不会等 sleep，失败路径的 loading 仍可能一闪而过。

正确做法是把“最小耗时”放在 finally 里补足：

```jsx
async function runWithMinLoading<T>(task: () => Promise<T>, minMs: number): Promise<T> {
  const start = Date.now();
  try {
    return await task();
  } finally {
    const elapsed = Date.now() - start;
    if (elapsed < minMs) await sleep(minMs - elapsed);
  }
}
```

成功路径耗时 = Max(请求耗时, 最小时间)；失败路径先补足剩余时间，再把异常抛出。两条路径体验一致。

### 6.4 节流与防抖的选型边界

| 场景 | 该用谁 | 原因 |
| --- | --- | --- |
| 按钮点击提交 | 节流（+ 状态锁） | 需要首次立即响应，只压制高频重复触发 |
| 输入框实时搜索 | 防抖 | 用户停止输入后才值得发请求 |
| 滚动/resize 监听 | 节流 | 需要周期性执行，而非等停止 |
| 表单字段校验 | 防抖 | 停止输入后再校验才合理 |

误用代价：按钮用防抖 → 点击延迟几百毫秒才响应；搜索用节流 → 打字途中一路狂发请求。

### 6.5 搜索防抖的配套 Hook

```jsx
import { useState, useEffect } from 'react';

function useDebounce<T>(value: T, delay = 300) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delay);
    // 依赖变化即清除上一次定时器，实现“重新计时”
    return () => clearTimeout(timer);
  }, [value, delay]);

  return debounced;
}
```

本质是利用 useEffect 的清理函数充当“重置定时器”的动作。

## 七、基于 ahooks 的替代实现（无需从零手写）

ahooks 可以替代手写防抖节流 Hook，内部基于 lodash 的防抖/节流能力做了 React 场景优化：用 useLatest 规避闭包陷阱，组件卸载自动清理定时器，返回的函数引用稳定，不会触发子组件无效重渲染。

### 7.1 ahooks 分层防抖/节流能力清单

- **基础函数级防抖/节流**：useDebounceFn / useThrottleFn，直接对任意函数做防抖/节流包装。
- **值级防抖/节流**：useDebounce / useThrottle，专门针对状态值做防抖更新，输入框场景直接用。
- **Effect 级防抖/节流**：useDebounceEffect / useThrottleEffect，给 useEffect 加防抖能力，适配滚动、窗口 resize 场景。
- **异步请求级防抖/节流**：useRequest 内置防抖/节流模式，一行配置拿到自动 loading + 节流冷却 + 生命周期管理。

### 7.2 方案一：基于 useRequest 叠加最小 Loading 时长（轻量推荐）

```jsx
import { useRequest } from 'ahooks';

const sleep = (ms: number) => new Promise<void>((resolve) => setTimeout(resolve, ms));

async function runWithMinLoading<T>(task: () => Promise<T>, minMs: number): Promise<T> {
  const start = Date.now();
  try {
    return await task();
  } finally {
    const elapsed = Date.now() - start;
    if (elapsed < minMs) await sleep(minMs - elapsed);
  }
}

function SubmitButton() {
  const MIN_LOADING_TIME = 500;

  const { loading, run } = useRequest(
    () =>
      runWithMinLoading(
        () => fetch('/api/submit').then((r) => r.json()),
        MIN_LOADING_TIME
      ),
    {
      manual: true,
      throttleWait: 1000,
      throttleLeading: true,
      throttleTrailing: false,
    }
  );

  return (
    <button onClick={run} disabled={loading}>
      {loading ? '提交中...' : '提交'}
    </button>
  );
}
```

这个方案的边界：useRequest 的 throttleWait 只做节流频率控制，run 内部没有“请求进行中”的状态锁，防重主要依赖按钮 disabled={loading}。如果存在非按钮触发（键盘回车、程序化调用、第三方按钮组件忽略 disabled），慢请求场景仍可能重入。需要严格的 run 级防护时，用下面的方案二。

### 7.3 方案二：基于 ahooks 基础 Hooks 的完整版本

用 useThrottleFn + useLatest + useUnmount，显式加 runningRef 状态锁，补齐方案一的缺口：

```jsx
import { useThrottleFn, useLatest, useUnmount } from 'ahooks';
import { useState, useRef, useEffect, useCallback } from 'react';

const sleep = (ms: number) => new Promise<void>((resolve) => setTimeout(resolve, ms));

async function runWithMinLoading<T>(task: () => Promise<T>, minMs: number): Promise<T> {
  const start = Date.now();
  try {
    return await task();
  } finally {
    const elapsed = Date.now() - start;
    if (elapsed < minMs) await sleep(minMs - elapsed);
  }
}

interface AntiRepeatOptions {
  wait?: number;
  minLoadingTime?: number;
}

/**
 * 通用防重提交 Hook：节流冷却 + ref 状态锁 + 最小 loading
 */
function useAntiRepeatSubmit<T extends (...args: any[]) => Promise<any>>(
  action: T,
  options: AntiRepeatOptions = {}
) {
  const { wait = 1000, minLoadingTime = 300 } = options;

  const [loading, setLoading] = useState(false);
  const latestAction = useLatest(action);
  const runningRef = useRef(false);
  const isMountedRef = useRef(true);

  useEffect(() => {
    isMountedRef.current = true;
    return () => {
      isMountedRef.current = false;
    };
  }, []);

  useUnmount(() => {
    runningRef.current = false;
  });

  const { run: throttledRun } = useThrottleFn(
    async (...args: Parameters<T>) => {
      // 状态锁：慢请求期间的重入在这里被拦住
      if (runningRef.current) return;

      runningRef.current = true;
      if (isMountedRef.current) setLoading(true);

      try {
        await runWithMinLoading(() => latestAction.current(...args), minLoadingTime);
      } finally {
        runningRef.current = false;
        if (isMountedRef.current) setLoading(false);
      }
    },
    { wait, leading: true, trailing: false }
  );

  const reset = useCallback(() => {
    runningRef.current = false;
    setLoading(false);
  }, []);

  return { run: throttledRun, loading, reset };
}

// 业务使用示例
function MyForm() {
  const submitApi = async (data: { name: string }) => {
    return fetch('/api/submit', {
      method: 'POST',
      body: JSON.stringify(data),
    }).then((res) => res.json());
  };

  const { run: handleSubmit, loading } = useAntiRepeatSubmit(submitApi, {
    wait: 1000,
    minLoadingTime: 500,
  });

  return (
    <button onClick={() => handleSubmit({ name: 'test' })} disabled={loading}>
      {loading ? '提交中...' : '提交'}
    </button>
  );
}
```

### 7.4 关键技术点补充

- **为什么最小 loading 放在 finally 补时，而不是 Promise.all**：Promise.all 只在成功路径上保证 Max(请求耗时, 最小时间)；失败路径会立即 reject。runWithMinLoading 的 finally 补时让两条路径一致。
- **useLatest 的作用**：确保节流函数内部始终拿到最新的 action 引用，彻底解决闭包陷阱。
- **useUnmount 的作用**：组件销毁时重置状态锁，避免已卸载组件上的无效更新。
- **timer 不要用 useState 存**：useUnmount 的回调只执行一次，闭包捕获的是首次渲染时的值。定时器句柄应放 useRef，这与 6.1 的原则一致。

## 八、总结与速记

- 节流管频率，状态锁管状态，两者是互补而非替代关系。
- 锁一律放 useRef，用 useState 做同步判断会踩闭包陷阱。
- 锁的释放必须写在 finally，否则一次接口异常就会导致按钮永久禁用。
- 最小 loading 时长要在成功和失败路径都兜底，Promise.all 只兜住了成功路径。
- 定时器句柄放 useRef，不要用 useState 存 timer 再在 useUnmount 里清理。
- 优先复用成熟生态：ahooks 的分层防抖/节流能力覆盖大多数场景；但 useRequest 的 throttle 不等于请求级状态锁，严格场景仍需 runningRef。
- 冷却期点击不要静默丢弃，用 onReject 给一个轻提示，避免用户误以为按钮失灵。
- 面试一句话版本：“按钮防重我用 ref 状态锁做请求级精确拦截 + 节流做冷却兜底 + 最小 loading 时长在成功失败两条路径上做体验兜底，三层分别解决重入、闭包陷阱和视觉闪烁。”
